# Plan Review Snapshot: Billing Review Lite

Connect → bounded page → separate matching by-key detail → cost evidence →
intention → one minimal local historical receipt. Issue #8 adds next-page
navigation and controlled connection/read recovery to the #5/#6/#7 journey.

## Run

Node.js 22 or newer; no runtime dependencies or build step:

```sh
cd app
npm start
# Optional alternative loopback port: PORT=6287 npm start
```

Open <http://127.0.0.1:6285/>. The server binds only to loopback. TLS certificate
verification is required; do not disable it. No SAP key is bundled.

- **Connect to live SAP sandbox** uses a locally supplied key for this connection.
- **Use fixture demonstration** is an offline, two-page billing-request dataset,
  explicitly labelled Fixture demonstration. Next page replaces the first two
  rows with two different records (EUR/USD, including exact large/negative amounts).
- **Use synthetic billing-document fixture** has a separate bounded fixture profile
  and no SAP API identity. Its date/header relation are fixture-only semantics.
- Select a row, then **Review cost evidence**. **Back to list** restores that same
  page and selected-row focus. **Next page** clears old detail/evidence and any
  unconfirmed intention; select a new row explicitly. **Restart list** returns to
  page 1 using the current connection. There is no cached record accumulation.
- On Screen 3, Keep / Review options / Help / Later are intentions only. Saved
  requires write plus identical validated read-back. Receipt-save **Retry** is
  separate from **Retry read**. Refresh/Reopen retains historical provenance,
  without reconnecting. Reset requires confirmation; uncertain storage is never
  falsely displayed as Saved. Receipt v2 retains coverage/assessment limitations;
  v1 remains untouched in unsupported-version recovery until deliberate reset.

## Coverage and pagination

Only server-provided supported continuations enable Next page; a full page never
manufactures an offset. Show current-page loaded/usable counts, partial coverage,
continuation exhaustion or rejected navigation explicitly. Absence of a next link
proves neither complete account history nor annual coverage. Explicit bounded completeness
is confined to known local fixtures, never SAP history. At most **20 successful
pages per traversal** are tracked, with only the current rows in memory; restart
to begin another traversal. Cycles/limit/rejected links offer recovery, not a false
completeness claim. Failed page reads clear prior rows and validity; Retry read
repeats the failed page, not the initial page. Restart/back-to-connection remain
explicit alternatives.

The sole live source is **API_BILLING_DOCUMENT_REQUEST_SRV v1.1.0, OData V2**,
at the fixed approved SAP sandbox service. The frozen OpenAPI documents `$skip`.
Supported continuation forms are absolute URLs, exact service-root paths,
`A_BillingDocumentRequest?...`, or `?...`, resolved only against that collection.
The adapter validates before attaching a key:

- HTTPS, exact approved origin/service/collection; no foreign ports, credentials,
  fragments, dot segments, malformed encoding or duplicate/unknown parameters.
- `$skip`: explicit nonnegative integer, at most 1,000,000; never generated by UI.
  `$top`: 1–10 (default 10); `$format=json`; fixed header `$select` and
  `$orderby=BillingDocumentRequest`. Omitted fixed options are restored canonically.
  A supplied projection/order must match. `$filter`, `$expand`, `$inlinecount`,
  `$skiptoken` and `skiptoken` are not followed: they are outside this reader's
  frozen query context / verified continuation contract.
- GET only, `redirect: manual`, 20-second upstream timeout, 5 MiB response limit
  (streaming reads stop at the bound), header page-size and 20-item limits.
  Redirects are refused without sending a second request or exposing Location.

Optional items remain not checked, unavailable, absent or partial as appropriate;
only explicitly bounded synthetic item coverage can be complete. An item failure
keeps otherwise valid header evidence, exposes its limitation and permits an item
read retry. Item continuations are **not followed** by this feature. No aggregation,
currency conversion or item-to-header monetary reconciliation is invented.

## Recovery and session state

| Result | User action / state |
|---|---|
| Valid empty page | No records, not zero spending; Retry read, supported Next page, Restart list or Back to connection. No snapshot/receipt is created; existing historical receipt stays unchanged. |
| 401/403 | Authentication/key problem. Old in-memory key is cleared. Correct key focuses the password input; explicitly reconnect, then select a row again. |
| Timeout / network / service failure | Distinct messages; Retry read remembers the list page, detail key or item operation within the current generation. No fixture fallback. |
| 429 / supplied Retry-After | Shared cooldown blocks equivalent live read controls. A different key/source or deliberate disconnect/reset abandons the old generation. |
| Malformed data / unsafe next / redirect | Distinct data/navigation recovery, not an empty or complete result; retry the valid operation or restart. |

Retry is **one user-initiated attempt**, never an automatic loop. Repeated clicks
cannot duplicate an in-flight read. Sanitized Retry-After supports integer seconds
and HTTP-date (IMF-fixdate, RFC850 and asctime wire forms). Valid delays are never clamped to a shorter wait;
countdown uses a monotonic browser clock, with availability feedback but no auto-send.
Missing/invalid 429 delays get an explicitly labelled one-second local debounce;
zero/past dates permit manual retry. Delays beyond representable clock range remain
blocked until the user abandons/corrects the connection. Source/key changes,
disconnect/reset and superseding page/selection requests invalidate old effects;
generation checks also ignore late responses. Background updates do not move focus.

Keys stay only in session memory/header transport, never URLs, storage, files or
logs. Corrected keys replace old ones. Fixture modes, disconnect/reset and reload
clear keys. Only the minimal receipt is persisted, never page cursors, retry state,
raw responses, full item arrays, names or contacts. Reads/retries never confirm an
intention or write a receipt.

## Source and monetary meaning

The [frozen #5 mapping](../docs/validation/issue-5-field-contract.md) and
[historical B0 report](../docs/validation/issue-5-b0.md) remain unchanged. Neither
these fixture tests nor injected live-mode transport establish new live acceptance.
The rejected CABILLINGDOCUMENT_0001 mapping is not reintroduced.

Amounts remain exact signed strings: header net p16/s3, tax p14/s3, gross p17/s3;
optional item net/gross p16/s3, tax p14/s3. No rounding, default NZD, FX, annual
totals or header-plus-item sum. Billing requests and their dates do not prove
payment, Spark customer identity or service coverage. Missing optional fields stay
Unknown/Not available; required data failures cannot become a usable zero snapshot.

### Versioned handoff to #7

`window.__issue6CostSnapshot` remains in-memory `issue-6-cost-snapshot-v1`:
original source/document/date/amount context, `materialInconsistency`, reasons and
assessment status. `rule.scope` is `synthetic-header-net-tax-gross-only` or
`source-and-linkage-validation-only`; linked monetary reconciliation is always
`not-assessed`. Synthetic consistent means only the declared header net+tax=gross
relation passed with exact BigInt coefficients at scale 3, not production validation.
Known source/parent/currency conflicts withhold item rows and restrict intentions
to Help/Later. Missing optional detail alone is not material inconsistency.
Back, page/selection refresh, source change and reset clear the pending export.
